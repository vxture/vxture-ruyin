# ADR-018 技能登记册：技能是契约工具的供给方，随发布预置，分三层

- 状态：**提议**（owner 2026-09-05 提出「按 harness 框架引入常用技能，不是从零添加，
  发布后已预置」；待 owner 定稿）
- 日期：2026-09-05
- 相关：ADR-006（skill 归 Ruyin，建在 Harness 上）、ADR-005（本地连接器）、
  ADR-013（渲染归 Runtime）、30-contract-schema §11（`tools[]` / `provider`）、
  TD-005（无沙箱不进 `execute_script` 类工具）、TD-034（连接器工具面）

## 背景：现在到底有什么

ADR-006 已经把话说清：**契约声明 `tools[]`（要什么），Runtime 提供其实现
（skill）**，分「预制（随 Runtime 内建）」与「拓展（用户 / 企业 / 产品安装，
协议对齐 MCP）」两层，且不对 skill 做任何权益门控。

但落地只到这一步：

| 层 | 设计里说的 | 实现里有的 |
|---|---|---|
| 预制 | 文件读写、检索、解析、结构化抽取、格式转换、导出 | `tool-executor.ts` 里一个写死的 `IMPLEMENTED` 集合：**四个** —— `read_file`、`write_document`、`search_knowledge`（有索引才算）、`export_result`（docx；pdf 靠壳，ADR-017） |
| 拓展 | MCP 对齐的连接器 | 连接器已落地（stdio，项目级授权），其工具面尚未接 Tool Gate（TD-034） |

没有登记册、没有清单端点、没有界面。一份产品契约只要声明了第五个
`provider: runtime` 的工具，任务在启动前就被拒，界面上写「本机跑不了这个任务：
还没有实现 X」—— 这句话是对的，但用户没有任何地方能看到「本机到底实现了哪些」。

设置里有「连接器」（拓展层的入口），没有技能层的入口。owner 的判断：**该有一个
能力集**，而且**不是让用户从零添加** —— 技能在开发与发布时就已经预置好。

## 决策（提议）

### 1. 技能的定义只有一个：契约工具 id 的实现

不引入与 `tools[]` 平行的第二套「技能」概念。**一个技能 = 运行时对某个工具 id
的实现**；契约是需求侧，登记册是供给侧，两边按 id 对上就接通 —— 与连接器工具
已经采用的规则完全一样（30-contract §11 `provider`）。

这条定死之后，「技能」在系统里就是可枚举、可核对的：契约要的每一个工具，都能在
登记册里查到有没有人实现、由哪一层实现、什么版本。

### 2. 供给分三层（ADR-006 的两层拆细，把「预置」显式化）

| 层 | 是什么 | 怎么到达用户机器 | 信任依据 | 能服务的类别 |
|---|---|---|---|---|
| **内建** builtin | 编进守护进程的实现 | 随安装包 | 与守护进程本体同一份签名 | 全部（`local_read` / `local_write` / `query` / `generate` / `export`） |
| **预置** bundled | 独立成包的技能，**随安装包一起发布**，放在 `resources/skills/<id>/`，各带清单与版本 | 随安装包；随应用更新一起更新，**没有独立的安装动作** | 与安装包同一份签名 —— 它是发布物的一部分，不是运行时从别处取来的 | 同内建（契约侧视为 `provider: runtime`） |
| **拓展** extension | 连接器（现有） | 用户 / 企业安装，项目级授权 | 用户显式添加 + 测试通过 | 只 `query` / `external_send`（R15 不变） |

「预置」正是 owner 说的「开发和发布后已预置链接」：技能在**发布时**打进包里，
用户拿到的是一台已经带着这些能力的机器，而不是一个空壳加一个商店。

R15 为什么不套在预置层上：R15 限制连接器工具的类别，理由是**第三方实现看不见
路径语义**，闸门无法替它核对参数落没落在授权目录里。预置层是我们自己的实现，
随安装包签名 —— 它的信任基础与守护进程本体相同，所以与内建一样归 `provider:
runtime`，Tool Gate 按契约里的 `input_schema` / `x-ruyin-ref` 照常核对。

### 3. 登记册：一份清单，一个端点，一个页面

**守护进程**维护技能登记册（`skill-registry.ts`）：

```ts
interface SkillEntry {
  id: string;                     // = 契约工具 id
  tier: "builtin" | "bundled" | "extension";
  version: string;                // 内建 = 运行时版本；预置 = 包清单版本；拓展 = 连接器报的
  categories: ToolCategory[];     // 它能服务的类别（供契约核对）
  description: string;
  state: "ready" | "unavailable"; // unavailable 带原因：依赖缺失（如 pdf 无壳）、被禁用
  detail?: string;
}
```

- `supportsTool(id, provider)` 改为查登记册，而不是查一个写死的集合。
- `GET /skills` 返回清单。任务启动前那句「还没有实现 X」保留，但**指向技能页**。
- 预置技能的清单文件 `resources/skills/<id>/skill.json`：`id`、`version`、
  `categories`、`description`、`entry`（见第 5 条）。守护进程启动时扫描一次。

**界面**：设置新增「技能」分区（顺序：账户 / 通用设置 / **技能** / 连接器 /
数据库 / 软件更新 / 关于）。**第一版只做清单，不做安装**：每一行是一个技能 ——
名称、层（内建 / 预置 / 拓展）、版本、状态、一句说明；拓展层那几行就是连接器
暴露的工具，链接到连接器页。「添加」不在这一页：预置的随发布来，拓展的走连接器。

### 4. 第一批预置什么：判据先于名单

判据（三条同时满足才进预置层）：

1. **确定性，不需要模型。** ADR-013 的分界线：渲染、解析文本层、格式转换、抽表、
   打包是技能；理解、生成、判断是模型能力（走能力面，ADR-009）。
2. **不需要 OS 级执行沙箱。** TD-005 不动：没有 `execute_script` 类。
3. **对标书这类文档型业务是常用的。** 不为「万一有人要」预置。

按判据筛出的候选（供 owner 勾选，不是定案）：

| 工具 id | 类别 | 做什么 | 现状 |
|---|---|---|---|
| `read_file` | local_read | 读授权目录里的文本文件 | 内建，已有 |
| `write_document` | local_write | 写文本 | 内建，已有 |
| `search_knowledge` | query | 项目内全文检索 | 内建，已有 |
| `export_result` | export | 渲染 docx（pdf 靠壳） | 内建，已有 |
| `list_files` | local_read | 枚举授权目录（名称、大小、时间） | 新 |
| `read_document` | local_read | docx / xlsx / **pdf 文本层** → Markdown（不做视觉理解，那是模型的事） | 新；docx 解析可复用 packages/document 的反向 |
| `extract_tables` | local_read | 从 docx / xlsx 抽出表格为结构化数据 | 新 |
| `read_spreadsheet` / `write_spreadsheet` | local_read / local_write | xlsx 读写（报价表、清单） | 新 |
| `fill_template` | local_write | docx 模板变量替换（标书封面、承诺函这类固定件） | 新 |
| `convert_document` | export | Markdown ↔ docx / pdf | 新；渲染部分已有 |
| `diff_documents` | local_read | 两版文档差异（配合人工核验） | 新 |
| `zip_package` | export | 把交付物打成一个包 | 新 |

**明确不进**：`execute_script`（TD-005）、任何联网抓取（那是连接器或能力面的
事）、任何「理解 / 生成」类（模型能力）。

### 5. 预置技能怎么跑

两种承载，按技能的性质选，不强求统一：

| 承载 | 用在 | 理由 |
|---|---|---|
| **进程内模块**（与内建同一条执行路径） | 纯转换类：渲染、解析、抽表、模板填充 | 已有 `packages/document` 这样的确定性库；进程内最简单、可测、无 IPC；它们不碰网络也不执行外部程序 |
| **MCP stdio 子进程**（复用 `mcp-client.ts`，从 `resources/skills/` 拉起） | 需要独立依赖、或将来要对第三方开放的 | 与连接器同一条协议与生命周期（拉起 → 握手 → `tools/list` → 停），审计说得清是谁在跑；出问题不拖垮守护进程 |

第一批候选全是纯转换类，**第一版只做进程内承载**；stdio 承载留给第二批。

### 6. 不变的几条

- **不门控、不计量、不计费**（ADR-006）。技能页上没有任何权益字样。
- **客户端零秘密**：技能不持有任何凭据；需要凭据的事走连接器或能力面。
- **Tool Gate 不变**：硬底线 ∧ 用户策略 ∧ 契约默认。技能只是「谁来跑」，不改
  「能不能跑」。
- **契约 schema 不改**：第一批全在 `provider: runtime` 之内，R 系列不动。

## 后果

- `IMPLEMENTED` 那个写死的集合被登记册取代；`supportsTool` 查表。
- 安装包多一个 `resources/skills/` 目录（第一版可以为空 —— 内建也在登记册里，
  页面照样有内容）。
- 任务被拒时用户第一次能看到「本机有什么、缺什么、缺的属于哪一层」。
- 未来若某个预置技能要独立于应用更新，再立 ADR 谈技能包的分发通道；**现在不做**
  （owner 口径：随发布预置）。

## 备选方案

| 方案 | 为什么不取 |
|---|---|
| 第二套「技能」概念，与契约 `tools[]` 平行 | 两套词表要对齐，而对不齐的那一刻任务照样启动失败；ADR-006 已经把技能定义为工具的实现，没必要再造一个 |
| 技能商店：用户从库里挑 | 与 owner 口径相反（不是从零添加）；而且第一批候选没有一个需要用户「挑」—— 它们是文档型业务的地板 |
| 全部做成 MCP 子进程 | 纯转换类走 IPC 只增加复杂度；进程内更可测。stdio 留给真需要隔离的 |
| 把预置技能套进 R15（只许 query / external_send） | R15 针对的是看不见路径语义的第三方实现；预置层与守护进程同签名，不该被自己的规则拦住 |
