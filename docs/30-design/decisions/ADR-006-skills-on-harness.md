# ADR-006 skill 层归 Ruyin，建在 Harness 上；权益门控只到产品级

- 状态：已接受（**部分取代 ADR-004**）
- 日期：2026-08-31
- 相关：ADR-001（模型通路，仍有效）、ADR-002（循环归属）、
  ADR-004（被本条部分取代）、ADR-005（本地连接器通路，随之简化）

## 背景

ADR-004 把 skill 与连接器判给 Runos，作为订阅权益到达。由此产生三个包袱：

1. Ruyin 是零密钥 public client，**够不到 Runos 的 S2S／MCP 面**；
2. 每个 skill 都要判权益，意味着**任务可能在中途被「未订阅」打断**；
3. skill 单独计量意味着在产品订阅费之外**再拆一层计费**。

## 决策

**skill 等能力由 Ruyin 自己提供，建在 Harness 之上，与 Runos 完全脱钩。**

**权益门控只到产品级。** 产品订阅了，产品之内的能力一律放开——
**不对 skill 做任何权益限制、不对 skill 单独计量、不对 skill 单独计费。**

理由：**订阅的粒度就是产品，不是能力。**费用已包含在产品价格里，
再拆分计费不合理。核心目标是业务功能的高质量与高效率实现，
而按能力计费恰好与之相悖——它让用户在干活途中为「还能不能用下一步」分心。

### 能力面因此重划

| 类 | 内容 | 供给 |
|---|---|---|
| **Ruyin 自有** | 本地文件接触、项目容器与本地存储、任务编排（Harness）、**skill 层（预制 + 拓展）**、工具过闸、人在回路、出口门控与审计、成果与导出、身份与权益接入 | Ruyin |
| **订阅得来** | **模型推理** | Atlas（ADR-001 通路不变） |

乙类由两项收缩为一项。判据变为：**除模型之外的执行能力，一律由 Ruyin 提供。**

### skill 与契约 tools 的关系

契约声明 `tools[]`（要什么），Runtime 提供其**实现**（skill）。两层：

- **预制** —— 随 Runtime 内建：文件读写、检索、解析、结构化抽取、格式转换、导出
- **拓展** —— 用户／企业／产品安装，协议仍对齐 MCP（40-context §4.2），
  但**不再从 Runos 取得**

## 后果

- **Runos 的 S2S 障碍随之消失**（就 skill 而言）。ADR-005 的待定项
  「连接器清单从哪来」不再指向 Runos；本地连接器成为 Ruyin 拓展机制的一部分。
- **Tool Gate 的目的收缩为纯粹的安全与用户控制**，不含权益维度。
  三层决策合成（硬底线 ∧ 用户策略 ∧ 契约默认）本就没有权益层，此处只是说清。
- **成本可见性不受影响**：推理由 Atlas 统一上报（通则），平台侧看得见成本，
  只是不向用户按能力拆分。Ruyin 侧无需为此做任何事。
- **R6 的理由需要修订。** ADR-004 曾把 R6（契约不得绑定 Provider）的理由归为
  「解析取决于订阅」。skill 不再受订阅约束后，R6 的理由回到更基本的一条：
  **契约要在两个运行时（本地／云端）跑出一致行为，因此不能绑定任一宿主的供给实现。**
- ~~产品级的 `limits`（如项目数上限）仍按通则在动作点执行。~~
  **澄清（同日，owner）：配额归 SaaS，Ruyin 不执行任何配额门控。**
  Ruyin 是**本地运行环境**；skill 由它自己实现，其前提正是「在本地可视为
  无限配额，或产品本就没有这类限制」。因此：

  | | Ruyin 做什么 |
  |---|---|
  | 订阅事实（`status` / `tier` / `bundled`） | **判产品能不能打开** —— 这是唯一的商业关卡 |
  | `limits`（上限型） | **不执行**。归 SaaS 侧 |
  | `quota_pools`（消耗型） | **不门控、不展示**。展示一个本地不执行的滞后数字只会误导 |
  | `QUOTA_EXCEEDED` 拒绝码 | **被动处理**：调用返回时如实呈现 + console 深链。这是当下事实，不是本地判定 |

  连带作废：契约「`limits` 键到动作点映射」的增补需求（原《能力登记册》缺口三）。

## 备选方案

| 方案 | 为什么不取 |
|---|---|
| 维持 ADR-004（skill 走 Runos） | 结构上够不到；且把计费拆到能力级，与产品定价重复 |
| skill 免费但计量上报 | 不计费却计量，只增加客户端复杂度，换不到任何决策依据——成本可见性已由 Atlas 侧满足 |

## 修订（2026-09-04，owner）：配额只读展示，仍不门控

「`quota_pools` 不门控、不展示」中的**不展示**撤回一半：标题栏的租户菜单
**只读展示** AI 配额（来自 C2 信封的 `quota_pools`，按指标合并、共享池只算
一次），参考平台端、按桌面端简化。**不门控、不计量、不执行 `limits`** 三条
不变 —— 它是平台上那个数字的镜子，不是本地判断；拿不到就说拿不到，不用
旧数字装作还在。理由：用户在台上干活时想知道「还剩多少」，这是信息，不是
关卡。

## 修订（2026-09-06，owner）：档位必须一致 —— 靠「只有一处判定」，不是靠两处判一样

owner 原话：**档位必须一致**。语境是「产品权益需要在 ruyin，和平台是一套的；
ruyin 是 SaaS 能力向桌面的延申，但数据不出域」。

### 这一条改了什么

此前 `tier` 在 ruyin 只当布尔用：`tier != null` 判产品能不能打开，档位的**值**
（基础 / 专业 / 企业）在本地不产生任何差别。现在它有意义了：**同一个档位，
在桌面和在 SaaS 得到同一组能力。**

### 怎么做到一致 —— 判定权收在一处

一致**不靠两边各判一次判成一样**（那是必然漂移的做法，客户端还可被改），
而靠**只有一处判定**：

- **判定权在产品的云端能力面。** 它持 OBO 票，读得到权威的权益事实；档位覆盖
  不到的能力，由它拒绝，拒绝码与 console 深链照 X-1 词表返回。
- **Ruyin 只做两件事**：① 忠实呈现能力面的拒绝，不改写、不猜原因；
  ② 可以按同一份权益事实把「这个档位没有」的入口**置灰**——那是呈现，不是判定。
- **置灰不得改变结果**：不得放行能力面会拒的，也不得拦下能力面会放的。用户点了
  照样发得出去，让能力面说不。这是「一致」的操作定义。

### 与既有三条的关系（都不变）

| | 变没变 |
|---|---|
| 产品级门控（能不能打开 / 新建） | **不变**，仍是 ruyin 唯一的商业关卡 |
| `limits` 不执行、`quota_pools` 不门控（只读展示） | **不变**。档位是**能力面**，配额是**用量**，两件事 |
| 不做商业推断、不自报计量 | **不变**。ruyin 不把 tier 送进回合请求 —— 能力面自己从票里读，送过去反而多一个可被篡改的来源 |

档位一致不需要把配额判断搬进本地，这一点必须写清楚：本条**不是**对
「配额归 SaaS」的松动。

### 待定（下一步要定的，不在本条范围）

界面要按档位置灰，就得知道「哪个任务属于哪个档位」。今天契约里没有这个信息。
两条路，各有代价，需要单独决策：

1. **契约声明**（例如 `tasks[].tier`）：ruyin 读得懂，能提前置灰，体验好；代价是
   把商业语义写进契约，与 R6「契约不绑定任一宿主的供给实现」的精神有张力，且
   档位调价要改契约。
2. **只由能力面运行时拒绝**：契约保持干净，判定唯一；代价是用户干到一半才知道
   这个档位不覆盖，与 `QUOTA_EXCEEDED` 今天的「被动处理」同一体验。

在定下来之前，实现按第 2 条走（它是第 1 条的地板，且不需要契约改动）。
