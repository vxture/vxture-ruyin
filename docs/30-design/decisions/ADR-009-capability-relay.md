# ADR-009 能力通路定案：经业务产品的云端服务中转

- 状态：已接受（落定 ADR-001 的待定项）
- 日期：2026-08-31
- 相关：ADR-001、ADR-008、平台《产品接入通则》C1b / Atlas 章

## 背景

ADR-001 已确定 Ruyin 不能直连 Atlas：Atlas 的产品身份取自 `act.sub`，拿到它
要 S2S 换票，换票要 `client_secret`，而**客户端零密钥**是本仓硬规则。当时留下
「提供方基址从哪来」为待定，三条候选：

1. 经业务产品的云端服务中转
2. 平台给 Ruyin 开面向客户端的能力入口
3. Atlas 支持用户级 token 直调

## 决策

**取第 1 条：能力解析到业务产品自己的云端服务，由它持凭据调 Atlas。**

理由：

- 与「业务产品由 SaaS 与 Ruyin 双侧接入授权」的既定思路自洽——业务产品本来
  就有服务端，那一侧本来就持 confidential 凭据。
- **不需要平台侧任何改动**，是三条里唯一今天就能落地的。
- 用量按通则「谁执行谁上报」由 Atlas 统一记账，Ruyin 依旧不计量（ADR-006）。

## 落地形状

- 契约**不带**提供方（R6 / Principle 4，见 ADR-001）。解析输入是契约里已有的
  `product.id` + 能力 id。
- 提供方基址由 **Runtime 单点配置**（`RUYIN_CAPABILITY_BASE`），不进契约——
  亦符合通则「不得成为第二处存放主机名的地方」。
- 协议是回合制（ADR-002）：发历史 + 上下文 + 可执行工具，收 `tool_calls` 或
  `content`。请求带 `taskId`（通则 X-2 跨产品聚合键）。
- **未配置基址时回落到 mock**，并如实标注——不能让「没接通」看起来像「跑通了」。
- 传输层失败包装成 `TransientError`，由 Harness 退避后停靠（50-harness 8.4）。

## 后果

- Capability Resolver 可以实现，mock 有了明确的替换点。
- 每个业务产品都要出一个能力面。这是这条路线的代价，也是它与「业务产品单独
  产品线」思路一致的地方。
- Runos 的能力目录同样够不到（同一个 S2S 障碍），故 skill 仍按 ADR-006 由
  Ruyin 自建预制；目录归位待障碍解决（ADR-008 遗留张力）。
