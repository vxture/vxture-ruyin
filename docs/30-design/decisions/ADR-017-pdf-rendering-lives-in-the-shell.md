# ADR-017 PDF 由壳里的 Chromium 渲染，字节回到守护进程落盘

- 状态：已接受
- 日期：2026-09-01
- 相关：ADR-016（结构化文档）、ADR-013（成果落盘）、ADR-008（运行时分层）

## 背景

ADR-016 交了 `.docx`，没交 `.pdf`。正式交付常常两样都要：`.docx` 给对方改，
`.pdf` 给对方看和存档。

守护进程里没有 PDF 渲染器，而**壳里已经有一个 Chromium**。剩下的问题不是
"用什么渲染"，是"渲染发生在哪个进程，以及落盘归谁"。

## 决策

**壳渲染，守护进程落盘。**

```
守护进程  export_result{format:"pdf"}
   → parseDocument(markdown)        结构化表示（ADR-016）
   → renderHtml(doc)                确定性转换，同构，无宿主 API
   → 经 utilityProcess 消息通道请求壳
        壳  → 离屏 BrowserWindow → printToPDF → 字节 → 回传
   → writeArtifact(path, bytes, grants)
```

### 为什么不引第三方 PDF 库

引一个库进签名客户端，换来的排版质量还不如已经装在同一个安装包里的
Chromium。ADR-013 说渲染引入依赖不与"不为解析引入本地库"冲突，但这条不构成
"随便引"的许可——**已经有的东西不该再引一份**。

### 为什么不让壳直接写文件

`writeArtifact` 是本宿主唯一的写入路径：授权护栏、大小上限、原子改名都在
那一处。壳自己写，等于开第二条写入路径，而**一条只贴合某一个调用方形状的
护栏，下一个调用方就绕过去了**——这句话已经写在工具执行器的文件头上，不该
由本条打破。

所以字节走一趟 IPC 回到守护进程。这不是浪费：一趟本机进程间拷贝的代价，
换的是护栏只有一处。

### 渲染模型输出的 HTML，脚本必须关掉

送进 BrowserWindow 的 HTML 由 Markdown 转来，而 Markdown 是模型写的。
`renderHtml` 逐节点构造并转义，正文里的原始 HTML 在 ADR-016 里已经被判为
lossy（拒渲），所以理论上进不来脚本。

理论上不够。离屏窗口 `javascript: false`、`sandbox: true`、
`contextIsolation: true`、`nodeIntegration: false`，页面自带严格 CSP。静态
内容排版不需要脚本，关掉不损失任何东西——**而"不需要"与"关掉了"是两回事**。

### 目录域在 PDF 里没有页码

Word 的 `::ry-toc` 渲染成 TOC 域，页码由 Word 打开时自己算。PDF 是定版的，
页码要在渲染时就知道，而知道页码要先排版——那得渲染两遍，第一遍找每个标题
落在第几页。

本版不做两遍。PDF 的目录是**带内部链接、不带页码**的标题清单，并**报一条
degraded**：内容都在，保真度降了，说出来。不说，用户会以为这就是目录该有的
样子。

### 独立运行的守护进程没有 PDF

守护进程可以脱离壳单独跑（开发时就是）。那种配置下没有 Chromium，
`export_result{format:"pdf"}` 如实报"本宿主没有接 PDF 渲染器"，而不是给一份
空文件或换成 docx。

装好的产品里守护进程总是跑在壳内，所以这条分支只在开发时出现。

## 后果

- 契约的 `format` 枚举恢复 `[docx, pdf]`。这不违反 ADR-016 第六条（只声明
  宿主真渲染得出来的格式）：在**发布形态**下两种都渲染得出来。
- 守护进程与壳之间从此有了一条**请求/应答**通道（此前只有壳轮询守护进程的
  HTTP）。消息按 id 配对，带超时——没有超时的等待，在壳崩了的时候会变成一个
  永远不返回的工具调用。
- 打包冒烟检查加一步：**真的渲染一份 PDF**，验字节以 `%PDF-` 开头。整条链
  （IPC + Chromium + 落盘）只有在打包形态下才完整，单元测试到不了。
