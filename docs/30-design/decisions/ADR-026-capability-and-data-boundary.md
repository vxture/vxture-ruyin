# ADR-026 能力与数据的边界：智能体不自建能力面，能力来自 Runos，数据留在本机

- 状态：**已接受**（owner 2026-09-15：§2 逐条当场定；§5 收口同日同意）
- 日期：2026-09-15
- **取代**：ADR-009（能力经业务产品的云端服务中转）
- **修订**：ADR-012（一级供给的来源）、ADR-018 / ADR-020（「产品分发」技能层的来源）、
  ADR-023（界面包的取回来源）
- 事实来源：vxture-runos origin/main `bd26817a`（原语只有 connector / skill / executor，`asset`
  不在生产范围；范围自陈「除模型推理之外」）；vxture-platform `#264` owner 答复；本仓
  `apps/local-host`（一项目一库 SQLCipher、`contract-fetch.ts` / `skill-distribution.ts` /
  `ui-fetch.ts` 三处都以 `RUYIN_CAPABILITY_BASE` 为来源）
- 相关：ADR-001（不直连 Atlas）、ADR-006（不门控不计量）、ADR-015（项目归属工作区）、
  ADR-025（能力调用两种路径）、RY-001 §07 #14 / #15

## 0. 一句话

**智能体不建服务端：它的定义随桌面包由平台分发到本机；调用智能体走已约定且畅通的 console 路径；
模型由产品直接对接 Atlas，不属于 ruyin；能力来自 Runos；它碰到的用户数据全部留在本机，不共享，单人使用。**

## 1. 为什么要改

ADR-009 当时选「每个业务产品自建云端能力面，由它持凭据调 Atlas」，理由是「不需要平台侧
任何改动」。落到今天：

- **一次都没通过。** bid 的云端能力面至今未建；装好的应用里模型回合走 `MockAIGateway`，
  智能体一次都碰不到本机能力（RY-001 §07 #8）。
- **每个智能体各建一套 = 重复建设**（owner）。能力平台本来就是为此而立的。
- 契约、技能分发、界面包三件事都顺着这条路线挂在「产品能力面」上，于是它们一起悬空。

## 2. 决定（owner，2026-09-15）

| # | 决定 |
|---|---|
| 1 | **智能体不自建能力面。** ADR-009 作废；`RUYIN_CAPABILITY_BASE` + `/products/{id}/capabilities/{cap}/turn` 这一套不再是目标形态 |
| 2 | **应用能力平台 = Runos。** 技能、远端连接器、沙箱执行，以及**平台级产品（数据平台、知识平台等）沉淀的资产**，经 Runos 服务多个智能体。走本机还是走云端按 ADR-025 |
| 3 | **调用智能体走 console；模型由产品直接对接 Atlas，不属于 ruyin。** 调用智能体的路径早已约定、完全畅通（owner；原文见《桌面端接入设计》2026-09-12：产品 webview 加载它自己的 web 应用、调它自己的后端，ruyin 只是窗口；console `GET /api/me/apps` 给出持有的智能体与 `homeUrl`）。**本机使用时模型回合同样由产品直接对接 Atlas**（owner），ruyin 不发模型回合；Runos 的范围不变（它不做模型推理）；桌面端仍不持任何下游令牌（#264） |
| 4 | **智能体的定义由产品提供。** 契约、技能包、界面包由产品设计；产品**针对桌面端运行打包**，登记到平台产品目录。**平台负责分发，ruyin 负责同步与本机存储** |
| 5 | **按需装到本机。** 用户可能订阅多个智能体：要在本机用的拉取安装，不需要的继续在云端使用 |
| 6 | **本机数据不出域。** 智能体需要的文档、数据连接器、生成的文档**全在本机**；智能体相关数据在它自己的库里（本机 SQLite，一项目一库加密），**不参与共享、单人使用** |
| 7 | **工作区之间的数据互通、知识互通是平台的工作，不是 ruyin 的。** 智能体需要哪些，由智能体设计和调用 |
| 8 | **桌面端列哪些智能体，按平台的「产品可露出端」`product_surfaces` 含 `desktop` 设计与获取**（owner；平台端正在实现）。字段未下发前按**未知**处理、不过滤 —— 未知不是「不能在桌面用」 |

### 2.1 ruyin 自己出本机的调用

| 调用 | 去哪 | 出去的是什么 |
|---|---|---|
| 会话、订阅、身份读 | console | 会话号，不含用户数据 |
| Runos 能力 | console → Runos（仅当 ADR-025 判定走云端） | 这次能力调用的参数 |

**模型推理不在这张表里**：它是产品直接对接 Atlas，不经 ruyin（owner）。

除此之外，**没有任何用户数据离开这台机器**：没有同步、没有备份上云、没有跨成员共享。

### 2.2 对 ADR-012 表格的更正

ADR-012 §背景那张表写「产品的智能（提示词、编排）不在本地，在产品自己的能力面」。按本
ADR 改为：**产品的智能随桌面包到本机**，由 Harness 在本机编排；模型由产品直接对接 Atlas。直接后果
要说清：**提示词与编排在用户机器上可读** —— 这是「智能体不建服务端」的代价，产品设计时
应当知道。

## 3. 由此改变的来源

| 东西 | 原来从哪来 | 改成从哪来 |
|---|---|---|
| 模型回合 | 产品能力面 `/turn`（ruyin 发起） | **不属于 ruyin**：产品直接对接 Atlas |
| 契约（ADR-012 一级） | 产品能力面 `GET /products/{id}/contract` | 平台产品目录的桌面包，经 console 同步 |
| 技能「产品分发」层（ADR-018 / 020） | 产品能力面 `/products/{id}/skills` | 随产品包；共享技能经 console 从 Runos 同步 |
| 界面包（ADR-023） | 产品能力面按摘要取回 | 随产品包；**契约钉摘要这一条不变** |
| 能力清单（ADR-020 §6.2） | —— | 经 console 从 Runos 同步 |

契约钉摘要、按摘要校验落盘、多版本并存、离线沿用最后一份 —— 这些**本机侧的规矩都不变**，
变的只是字节从哪来。

## 4. 本机要做的

**对接既有的 console 路径，不向平台提新需求**（owner：这条路径早已约定、完全畅通）。本机侧：

1. 读 console-bff 现有接口，把智能体调用、契约 / 技能 / 界面包同步对接到 console 路径上。
2. 把「从哪同步」收成一个统一的来源接口，契约、技能、界面包三处都走它。
3. 路由判定接入宿主工具执行（ADR-025）。
4. 装到本机**复用首页已有的「安装 ▾」**（「从本地包安装」「从产品库拉取」，owner 2026-09-04 定），不新增入口；「已订阅 · 本机未安装」卡只需把人引到那里（正式版装包的签名前提见已开的平台 `#274`）。

## 5. 收掉为同步预留的旧设计（owner 2026-09-15 同意）

| 项 | 现状 | 提议 |
|---|---|---|
| TD-043 同步引擎（40-context-architecture §8 整章） | 零实现，登记为「等云端数据面」 | 转 **standing（有意不做）**：ruyin 不同步智能体数据 |
| 契约 §14 `sync` 键 | 有校验、无消费者 | 只收 `local_only`；下一次契约大版本删除。**校验收紧是代码改动，另行登记**：随包夹具 `products/bidproposal` 的 `core: selective`、`generated: manual` 会因此不过校验，要同批改夹具，不在本文档 PR 里做 |
| 契约 §9 `context.types[].sources` 的 `cloud` | 可写，无通路 | 明确含义：**只指经 Runos 调用的云端能力或资产**，不指云端存储 |

## 6. 不变的

- 客户端零秘密；桌面端不持任何 `aud=<下游>` 令牌。
- Tool Gate 是第二层授权的唯一执行点，走本机、走云端都过。
- 权益门控只到产品级，不门控、不计量能力调用（ADR-006）。
- 项目必须归属工作区（ADR-015）—— 归属是边界，不是共享。

## 7. 备选方案

| 方案 | 为什么不取 |
|---|---|
| 维持 ADR-009，每个产品自建云端能力面 | 重复建设；至今未通 |
| 由 Runos 统一对外提供模型 | 要改 Runos 的产品范围（它的 ADR-003 排除模型推理）；owner 定：调用智能体走既有 console 路径，模型由产品直接对接 Atlas |
| 用 Runos 的 `asset` 原语装智能体定义 | `asset` 是给平台级产品沉淀的共享资产用的，不是智能体定义（owner 澄清） |
| ruyin 做工作区成员之间的数据同步 | 越界：数据互通是平台的工作；ruyin 只解决数据不出域 |

## 8. 追加（owner，2026-09-15）：设置 › 模型平台 —— 只展示，不调用

owner 要求在设置里「能力平台」之前加「模型平台」，并明确：**主要功能只展示，不是调用**；范围
**只列模型**（「用量和配额在平台端，不用复杂化」）。

**这不是对 §2 第 3 条的松动。** 模型仍由产品直接对接 Atlas；ruyin 不发模型回合、不选模型、
不配置模型、不持任何 key。这一格只把平台已有的事实展示给用户：本工作区被授权使用哪些模型。

- **取法是平台现成的会话读，不向平台提新请求**：console-bff `GET /api/atlas/models`
  （`atlas.router.ts`，在 `api/*` 下，桌面会话够得着；经 S2S 代理 Atlas `/tenancy/models`，
  已按本工作区授权过滤）。守护进程转成 `GET /platform/atlas/models`（RY-102）。
- **只投影展示字段**（`modelCode` / `modelName` / `provider` / `capabilities` / `isActive`）：
  平台记录里的 `endpointUrl`、`keyReference`、`config` 是运维信息，不出守护进程。
- **可见性照平台的角色**：`tenant.model.read` 只授租户所有者（vxture-platform 迁移
  2026-09-14，批 7）。其他角色看到的是「只有租户所有者能查看」，ruyin 不绕过、不另判。
- 用量（`/api/atlas/usage`，Atlas 请求日志，非计费）与配额不放：owner 定不做。
