# ADR-010 验证的工作界面：检查归产品，编排归 Runtime

- 状态：已接受
- 日期：2026-08-31
- 相关：30-design/50-harness.md §7、60-operations/10-tech-debt.md TD-016

## 背景

契约声明 `verification: [{id: source_traceability, kind: automated}]`——只有
名字，**没说要检查什么**。Runtime 拿到这个字符串无从求值。

50-harness §7.1 写着 automated 是「确定性规则（结构／覆盖／一致性检查），
**本地执行**」，于是曾把它理解为「Runtime 要内建一批检查」，并为「检查目录由
谁定义」立了 TD-016。

原实现更糟：`automated` 与 `ai_assisted` **都硬编码返回 `passed`**——那不是
桩，是在谎称验证通过。已改为升级给人。

## 决策

**自动检查是产品侧的事，Runtime 不介入检查内容。**

界面划分：

| 事 | 谁做 |
|---|---|
| 声明规则（`id` + `kind`） | 契约 |
| 排序、调用、收结果、失败进修订轮、终点交人、留痕 | **Runtime** |
| **实际检查什么** | **产品的能力面** |

推论：**`kind` 从「在哪执行」降级为「代价／排序提示」。** `automated` 与
`ai_assisted` 都解析到产品能力面（ADR-009 的同一条通路），区别只是前者确定性、
便宜，该先跑——这正好就是 §7.1 的「按代价升序、快速失败」。

## 后果

- **TD-016 消失**：没有「Runtime 内建检查目录」这回事，不需要词表决策。
- **50-harness §7.1 的「本地执行」需更正**——那句话与本裁定冲突。
- 实现从「automated 一律升级给人」改为「调用产品能力面，只有答复读不懂时才
  升级」。读不懂即升级这条不变：往「通过」方向猜，正是让验证退化成装饰的方式。
- 产品能力面因此要能回答 `verify:<rule>`，与生成能力同一通路。
