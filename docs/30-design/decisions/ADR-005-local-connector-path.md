# ADR-005 本地资源连接器：第二条通路

- 状态：已接受
- 日期：2026-08-31
- 相关：ADR-001（能力通路）、ADR-002（循环归属）、ADR-004（能力供给边界）、
  30-design/40-context-architecture.md §4、30-design/50-harness.md §5、
  60-operations/10-tech-debt.md TD-005 / TD-012

## 背景

ADR-004 确定 skill 与连接器由 Runos 供给、经订阅到达，Ruyin 只做接入。但云端
skill **够不到本机文件与局域网**——而那正是 Ruyin 存在的理由。因此需要第二条
通路：连接器在**本机**执行。

## 决策

**按资源位置二分通路。**

| 通路 | 资源位置 | 路径 |
|---|---|---|
| 一 · 云端 | 云端知识、外部 SaaS API | 业务产品服务端 → Runos / Atlas |
| 二 · 本地 | 本机、局域网、私有服务 | 守护进程 ↔ 本地 MCP 连接器 |

判据是**资源在哪**，不是能力属于谁。通路二不改变 ADR-004 的供给边界：连接器
仍由 Runos 供给、受订阅约束，Ruyin 只负责在本机把它跑起来并过闸。

### Harness 侧的插入点

`ConnectorPort` 就是接缝——MCP 连接器是它的另一个实现，**Harness 主体不改**。
但接缝本身要补齐五处：

1. `Binding.source` 由字面量 `"local"` 放宽为 `ContextSource` 联合
2. connector id **记在 `ContextItemMeta` 上**，不再由 `source` 约定推导
   （现 `metaConnector()` 的推导在两个同源连接器下必然撞车）
3. `ContextItem.content` 支持二进制承载
4. 连接器注册表由构造期静态 `Map` 改为可动态注册（装新连接器不必重启守护进程）
5. `ConnectorPort` 增加生命周期与健康检查

### 另需一个新端口

`ConnectorPort` 只覆盖**读**。MCP 连接器天然提供**工具**（回写内网系统、触发
内部流程），而 `ports.ts` 目前**没有任何工具执行端口**。通路二须补一个，并让
Tool Gate 坐在它前面。

## 安全边界

**不违反 TD-005，理由是「谁决定跑什么」：**
`execute_script` 类工具是 **AI 在任务中决定**执行任意代码；本地 MCP 连接器是
**用户／企业在安装时决定**装哪个，AI 只能调用其已暴露的工具。后者与「用户装了
一个软件」同级。

信任模型四条：

1. **来源受限** —— 来自 Runos 或产品包，不接受任意 URL
2. **显式安装** —— 用户确认，不静默拉起
3. **签名验证** —— 复用 `.ruyinpkg` 管线（受 TD-012 阻，信任锚未就位）
4. **授权以项目为边界** —— 与文件夹 Grant 同级，非全局放行

门控与留痕不因连接器在本地而放宽：取回数据进 Context Set，送推理**过传输门**；
连接器写操作属 `external_send` 类，**硬底线 ≥ ask，契约不得放宽**；每次调用落
审计（连接器、资源、内容哈希，不落原文）。

## 分发通路（依 ADR-006 简化）

原待定项「连接器清单从哪来」在 [ADR-006](ADR-006-skills-on-harness.md) 后不再
指向 Runos：skill 与连接器归 Ruyin 自建，**不受订阅约束**。因此本地连接器
成为 Ruyin **拓展机制**的一部分，Runos 的 S2S 障碍就此消失。

分发落到两条，都在本仓可控范围内：

| 来源 | 说明 |
|---|---|
| **预制** | 随 Runtime 内建（`local-fs` 及后续预制连接器） |
| **拓展** | 用户／企业／产品安装；协议对齐 MCP，复用 `.ruyinpkg` 的签名与安装管线 |

安全边界与门控要求不因此放宽——本文「安全边界」一节全部照旧生效，
**且因 skill 不再有权益关卡，Tool Gate 成为唯一的把关点，不能再拖。**
