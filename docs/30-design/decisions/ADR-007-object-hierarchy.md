# ADR-007 对象层级：workspace 让给平台定义，本地容器是项目

- 状态：已接受
- 日期：2026-08-31
- 相关：ADR-006、30-design/10-workspace-runtime.md §5.2、
  60-operations/10-tech-debt.md TD-013、平台《产品接入通则》C2

## 背景

「workspace」一词在两侧各有定义，且**同屏出现**：侧栏身份区显示平台租户
工作区，主区列本地容器。通则 X-4 禁止靠上下文区分——这里连上下文都区分不了。

两个定义摆在一起看，矛盾不在措辞，在**层级**：

| | 平台 | Ruyin（原定义，10 §5.2） |
|---|---|---|
| workspace 是什么 | 隶属 tenant，**订阅的主体** | 用户当前处理哪一个业务上下文 |
| 与产品的关系 | workspace **包含**产品（订阅了哪些） | 产品**包含** workspace（几个在办的案子） |

相对「产品」，两者是反的：平台的在产品之上，Ruyin 的在产品之下。它们不可能
是同一个东西。

## 决策

**「workspace」让给平台定义；Ruyin 的本地容器称「项目 / Project」。** 一条链：

```text
Tenant（个人也有 personal）
  └── Workspace          平台定义：订阅主体
        └── 已订阅的产品
              └── 项目    Ruyin 的本地容器
                    └── 任务
```

**项目归属于工作区。** 订阅、权益、数据边界都按工作区划，因此切换工作区应当
看到不同的项目——A 工作区的投标项目不该出现在 B 工作区里。

## 后果

- 内核符号 `WorkspaceRuntime` / `WorkspaceStore` / `WorkspaceMeta` 等管理的是
  **项目**，随之改名为 `Project*`；本地 API `/workspaces` → `/projects`；
  契约顶层 `workspace:` → `project:`。
- **新项目 id 用 `prj_` 前缀，既有 `ws_` 保留不动。** 审计链的创世哈希是
  `sha256("genesis:" + id)`，**改既有 id 会作废每一条链**。id 不透明，混着无害。
- **`Workspace Runtime` 这个规范名不改，且含义变准了**：从「管理工作空间的
  运行时」变成**「在工作区内运行的运行时」**——这正是 Ruyin 做的事（登录拿到
  `active_workspace`，在其中跑它订阅的产品；C2 权益本就按 `workspace_id` 取）。
- 项目记录需带来源工作区，并按它过滤。**这会改变用户看到的东西**，是本条最
  直接的用户可见后果。
- TD-013 据此收口。
