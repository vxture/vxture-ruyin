# ADR-008 一个内核两个宿主；Runos 是能力供给层，不是对位运行时

- 状态：已接受（**修订 ADR-004 / ADR-006 中的分层表述**）
- 日期：2026-08-31
- 相关：ADR-004、ADR-006、30-design/60-technical-architecture.md §6.2

## 背景

曾提出「Runos 是 SaaS 侧运行时，Ruyin 是桌面侧运行时」。核对 Runos 实际形态
后，这个类比在层级上不成立。

Runos 的十四个板块是：能力目录、注册与晋级、活体校验、身份、授权闭包、
**凭证代理**、策略、配额、发现、审计、消费契约（四工具面）、沙箱执行器
（未启用）。它自陈 **「Skill 走分发而非执行」**，并把嵌入/向量后端判给
Atlas（「不在本仓造」）。

它**没有**工作区、任务状态机、人在回路、上下文选择、业务契约——**它不是
运行时，是能力供给层**，而且它对 Atlas 同样是消费关系。

Ruyin 在 SaaS 侧的真正对位是 **Cloud Runtime**（10 §15 已 posit，尚未存在）。

## 决策

**分层如下，Atlas 与 Runos 给两个运行时同时供货：**

```text
              业务产品（契约）
                    │
        ┌───────────┴───────────┐
   Ruyin（桌面宿主）      Cloud Runtime（云宿主）
        └──── runtime-core（共享内核）────┘
                    │
        ┌───────────┴───────────┐
    Atlas（模型）        Runos（能力目录·网关）
```

**两个宿主共享一个内核，不是两套实现。**

## 为什么这条值得写下来

问题里叠了两件事，分开看结论完全不同：

- **两个执行环境（桌面 + 云）**——数据驻留要求逼出来的，**不是选择**。
- **两套实现**——是选择，而且是最贵的那部分。

行业样本很清楚：

| 路线 | 样本 | 结果 |
|---|---|---|
| 共享内核 + 多宿主 | React（一个 reconciler，react-dom / react-native）、SQLite | 语义天然一致，**因为核心就是同一份代码** |
| 规范 + 多实现 | 浏览器（HTML/CSS + WPT）、SQL、Java EE（TCK） | 极贵、极慢、**仍然分叉**；「标准 SQL」至今是愿景 |
| 协议优先 | LSP、MCP、OCI/CRI | 协议是持久资产，实现可替换 |
| 云优先 + 瘦本地 | Codespaces、云端 agent | **数据必须出域**，与 Ruyin 定位冲突 |

Ruyin 现有架构已经站在第一行：`runtime-core` 宿主无关、发布为 npm 包、
Cloud Runtime 消费它而非重写。**照「两个运行时」的说法做，会把架构推到第二
行——工业界公认最贵、最容易分叉的那条。**

## 模型与数据边界

- **模型能力全面由 Atlas 提供，不足由 Atlas 补齐。** 因此 `/v1/parse` 返 501
  是 **Atlas 的能力缺口**，不是 Ruyin 引入本地解析库去绕过——签名客户端因此
  少一批依赖，也少一处要维护的解析器。
- **数据不驻留域外，但推理时受控外发。** 04 §7.3 的原表述即
  「推理传输 ≠ 数据存储」：传输事件标 `persistence: none`，审计只落内容哈希。
- **硬边界要说清**：对涉密网／物理隔离客户，「不出域」是合规红线，在线推理
  根本不可能。那类场景要等本地模型，**当前不覆盖**。

## 对 ADR-004 / ADR-006 的修订

- ADR-004 把 skill／连接器判给 Runos 并受订阅约束——**该分层部分作废**，
  订阅约束部分已由 ADR-006 废除。
- ADR-006 的结论（skill 层归 Ruyin、门控只到产品级）**仍然有效**，但理由更新：
  不是「Runos 够不到所以自建」，而是 **Ruyin 是执行环境，Runos 分发不执行**。
- **遗留张力**：能力目录放在 Runos 分层上更干净，前提是先解决「Ruyin 怎么
  够到 Runos」——与 Atlas 同一个障碍，见 ADR-009。
