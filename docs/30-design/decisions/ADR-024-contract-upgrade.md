## 0. 一句话

**产品发了新版本，既有项目不会自己变；人在项目里点「升级」，Runtime 先核新契约对
这个项目的快照「只增不删、不改窄」，核过了才换快照。** 放宽了的安全相关声明（去掉人工
确认、工具默认放松、敏感度调低）不拦，但升级前**逐条摆给人看**。

## 1. 现状

项目创建时把当时的契约**快照**进项目库（`putContract`），此后一切 —— 状态机、任务、
工具闸、`/bridge/*` 裁剪、产品界面装哪份 —— 都按这份快照走。**快照本身是对的**：产品
升版不会打断半截的工作，这是有意的设计（TD-048 原文）。

缺的是**「升上去」这条路，一条都没有**：产品发了 1.1，老项目永远停在 1.0；ADR-023 之后
连产品界面也跟着停在老版本。第一个真实产品一旦有了用户与老项目，这条路再补就是在带病
的数据上补 —— 所以在它来之前做。

## 2. 决定

### 2.1 升级是**人发起、逐个项目**的，不自动

- 产品库里的生效版本（`registry.contractOf`，新项目也用它）高于项目快照的版本 → 项目里
  出现一条「产品有新版本」，**人点了才升**；
- **不批量、不自动**：自动升等于替每个项目的主人做了决定，而升级改变的是他正在用的
  东西（任务、界面、默认权限）；
- **不回退**：升级之后新版本加进来的类型、任务可能已经产出了数据，退回旧快照会把它们
  变成契约里不存在的孤儿。回退要的是「新版本坏了」时切产品库的生效版本（§18.4 已有），
  不是把项目退回去。

### 2.2 核什么：**新契约对快照「只增不删、不改窄」**

§18.4 已经写了规则（patch 不改语义、minor 只增不删、major 附迁移声明），但**不信版本号
标签，信实际的差异** —— 一个标成 minor 却删了东西的版本，照样拒，并且说清删了什么
（那是产品违反了规则，静默采纳会把它藏起来）。

| 契约段 | 算「删 / 改窄」（拒） | 不拦 |
|---|---|---|
| `objects` | 删对象、删关系、换主对象 | 新增 |
| `states` | 换挂载对象；删状态；删一条既有的转换 | 新增状态与转换；改 `initial`（只影响新项目） |
| `context.types` | 删类型；`required` false→true（既有项目可能没绑它，任务突然起不来）；删来源；改 `class` | 新增类型；加来源 |
| `capabilities` | 删能力；改 `kind` | 新增 |
| `tools` | 删工具；改 `category`；改 `provider` | 新增 |
| `tasks` | 删任务；删它声明过的 `output_types` | 新增任务；任务的其余字段 |
| `project.type` | 改（continuous ↔ project 是容器形态） | — |

`input_schema` 的变化**不在检查范围内**：参数由产品自己的能力面在回合里生成，项目里不
留存旧的调用去对它。

**核的时刻**：升级之前那一下，而且**只在没有未落定任务时**（与归档同一条前提）：跑到一半
的任务一边按旧快照、一边按新快照，谁都说不清它该听哪一份。

### 2.3 放宽的**不拦，但摆出来**

以下变化让项目**更松**，是产品的权利（默认值由契约定），但人应当在点「升级」之前看见：

- 转换去掉了 `confirm: human`；
- 工具的 `default` 放松（deny→ask、ask→allow）、`risk` 调低；
- 上下文类型的 `sensitivity` 调低；
- 权限默认值（`permissions`）放松。

**工具闸的硬底线不受影响**：`external_send` ≥ ask 以 `stricter()` 合并且不可配置（R7 / R10），
契约放宽不了它；用户自己在项目里设过的工具策略照旧生效（TD-050）。

### 2.4 升了之后

- 换快照、更新 `productVersion` / `contractVersion`，审计记 `project.upgraded`（从哪一版到
  哪一版、加了什么、放宽了什么）；
- **产品界面跟着换**（ADR-023：界面按快照钉的摘要装）；界面包还没取回的，就是「暂时不可用」，
  那一格里有「重新获取」；
- 产品级凭据**不作废**：凭据按 (项目, 产品) 限定，不按版本；裁剪按新快照，立刻生效；
- 发 `project` 事件：产品界面与工作台都重问一次。

### 2.5 检查器放在 `contract-schema`

`compareContracts(snapshot, next) → { verdict, removed[], narrowed[], loosened[], added[] }` 是
纯函数，放在**同构的 `contract-schema` 包**里 —— 云端运行时升级项目时用的是**同一个**检查器
（Same Validator, Any Runtime，§4）。内核的 `upgradeProject` 调它，宿主不重写一份。

## 3. 不做的

- **major 迁移**：迁移声明的格式还没定（§19 Open Questions）。大版本（或者核出了删 / 改窄）
  如实说「这一版对这个项目不兼容，需要新建项目」，不提供半截的迁移；
- **批量升级、自动升级**：见 2.1；
- **跨产品**：一个项目只属于一个产品（ADR-007 / 015），升级不改变这一点。

## 4. 分片

1. **`compareContracts`**（contract-schema）：纯函数 + 用例（每一类删 / 改窄 / 放宽各一条，
   同版本号、标签撒谎的各一条）；
2. **`upgradeProject`**（runtime-core）：前提（没有未落定任务、未归档、目标版本更高、检查
   通过）、换快照、审计；
3. **守护进程 + 界面**：`GET /projects/:id/upgrade`（有没有新版本、能不能升、加了 / 放宽了
   什么）与 `POST`；项目里一张「产品有新版本」的卡，放宽项逐条列出，点了才升。

每一片都能在没有真实产品的情况下验证：用内置夹具改出一个 1.1（只增）和一个撒谎的 1.1
（标 minor、删了东西）。

## 后果

- TD-048 的回收条件（「定义升级语义」）由本 ADR 给出，实现落地后关闭。
- 契约规范 §18.4 接受后补一段：规则由 `compareContracts` 执行，版本号标签只作参考。
- 产品方得到一个明确的约束：**想让老项目跟上，就只增不删**；删了东西的版本只能给新项目。
