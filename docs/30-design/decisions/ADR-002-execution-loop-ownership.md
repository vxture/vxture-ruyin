# ADR-002 执行循环归 Harness，云端只出无状态推理

- 状态：已接受
- 日期：2026-08-31
- 相关：ADR-001、30-design/50-harness.md §4／§5／§6、30-design/10-workspace-runtime.md §8

## 背景

云端 agent 自身是一个循环体，Harness 也是一个循环体。**两个循环不能嵌套，
必须有一方让位。** 这个归属决定了工具在哪执行、门控在哪生效、审计链在哪闭合、
人在回路能否插入——因此它决定了 Ruyin 是否还有存在价值。

## 决策

**循环留在 Harness（本地）；云端只提供无状态推理。**

每一回合：Harness 把历史 + 本轮上下文 + 本地可执行的工具清单发给能力提供方，
得到 `tool_calls` 或 `content`；若是 `tool_calls`，工具在**本地**过 Tool Gate
后执行，结果并入历史进入下一回合。

## 后果

- **`AIGatewayPort` 现签名必须改。** 当前 `invoke({capability, inputs}) →
  {content}` 没有历史、没有工具、返回没有 tool_calls——**在类型层面就排除了
  50-harness §4 的循环**。此刻只有 mock 一个实现，改动成本最低。
- **能力必须串联。** 当前直线 for 循环让每个能力拿到同一份输入，能力之间互不
  相见；接上真模型只会得到互不相干的多段文本。
- **执行必须转后台。** 真实推理每回合十秒到一分钟，不能同步占住一次 HTTP 请求。
  这同时是恢复语义（50-harness §8）的落点。
- Tool Gate、Checkpoint 队列、journal 恢复据此依次解锁（顺序见下）。

依赖链，前一环不动后一环写不了：

1. 网关端口改回合制 → 2. 循环真正成为循环 → 3. 执行转后台 + 状态可查
→ 4. Tool Gate → 5. Checkpoint 升级为队列 → 6. 恢复接上 journal

前三项是一个不可分割的包，且**全部是本地重构，不依赖平台侧决定**。

## 备选方案

| 方案 | 循环在哪 | 为什么不取 |
|---|---|---|
| agent 全权 | 云端 | 工具调用发生在云端 ⇒ 碰不到本地文件；人在回路插不进；审计链断在云端；Tool Gate 形同虚设。**等于取消 Ruyin 存在的理由** |
| 双层回调（MCP 式） | 云端循环 + 回调本地 | 技术可行，但需长连接与跨网门控协同；复杂度换不来额外能力 |

> 对 Ruyin 而言，「借助 SaaS 能力」借的是**推理**，不是**代办**。
