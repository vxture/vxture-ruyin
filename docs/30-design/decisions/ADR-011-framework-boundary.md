# ADR-011 框架边界：Runtime 给事实，产品给措辞与判定

- 状态：已接受
- 日期：2026-08-31
- 相关：ADR-002、ADR-009、ADR-010、30-design/50-harness.md §7

## 背景

Ruyin 是**一套框架**，不是一个超级智能体。框架提供机制与保证；业务语义、
措辞、编排策略归产品。这条界线说起来清楚，实现时容易滑过去——复查后发现
内核有三处已经滑过去了：

| 越界 | 内核做了什么 | 为什么是产品的事 |
|---|---|---|
| `renderContext()` | 把目标 / 约束 / 上下文**拼成一段提示词文本** | 措辞是领域知识所在，拼提示词等于把这部分工作接管过来 |
| 修订轮 | 内核**撰写**了「verification failed… revise the work to address:」 | 同上，这是提示词 |
| 验证判定 | 内核**用正则读散文**找 `PASS` / `FAIL` 前缀 | 框架该定**形状**，不该解释业务语言；而且猜错的方向是「通过」 |

第三条尤其糟：既越界，设计也弱——拿正则判断一次验证过没过。

## 决策

**Runtime 传结构化事实，产品负责措辞与判定。**

请求侧：`objective` / `constraints` / `context[]` 作为字段传出，`messages`
只装**对话本身**（提供方答了什么、工具返回了什么）。首个能力面对的是空对话——
开场怎么说，由提供方决定。

修订轮：失败项以 `revision: { round, failures[] }` 作为**数据**传出，内核不再
写「请修正」这句话。数据在下一轮生成后即清除，免得后续每个回合都收到一个
已经处理过的失败。

应答侧：新增 `verdict` 变体（`{ passed, reason? }`）。**判定是字段，不是待解析
的句子。** 非判定形状的应答一律升级给人——不去猜。

## 后果

- 内核不再持有任何提示词文本；`renderContext` / `renderValue` 删除。
- 生成类能力若返回 `verdict`，判为提供方用错接口并显式失败——比给它编一个
  含义好。
- 同一份事实在两个运行时上形状一致，措辞各自决定：这比内核统一拼词更能让
  「同一契约、任一运行时」成立，因为分歧被挡在了措辞层而不是事实层。

## 判据（供后续自查）

Runtime **提供**：项目容器与本地存储、本地文件接触与授权、任务编排（状态机 /
循环 / 恢复 / 取消）、工具过闸、人在回路的呈现与记录、出口门控与哈希链审计、
成果与导出、身份与权益接入。

Runtime **不提供**：业务语义、提示词、模型选择、agent 编排策略、验证规则的
内容、定价与商业设计。

**一句话自查：这段代码在决定「怎么说」还是「有什么」？前者就是越界了。**
